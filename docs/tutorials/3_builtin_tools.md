# 内置工具（Built-in Tools）完全指南

作为 coding agent，核心能力不仅体现在对代码逻辑的理解与生成上，更体现在与外部环境的高效交互之中。本教程将系统性地介绍当前默认 agent worker（`src/kimix/agent_worker.json`）所拥有的全部**内置工具（Built-in Tools）**，并深入讲解如何在提示词（Prompt）中精准地引导 agent 调用这些工具，以完成从文件操作、代码执行、信息检索到复杂任务编排的各类工作。

> **注意**：`agent_worker.json` 通过 `extend: default` 继承基础配置，但由于显式重写了 `tools` 字段，最终可用的工具集**仅包含** `agent_worker.json` 中列出的 26 个工具。以下列表即为实际可用的完整配置。

## 什么是内置工具

内置工具是 agent 与操作系统、文件系统、网络以及外部进程进行交互的**标准化接口**。每一次工具调用都是一次结构化的 Function Call，agent 根据当前任务的上下文自主决策是否需要调用工具、调用哪个工具以及传入哪些参数。

理解并善用这些工具，意味着你可以让 agent 做到：

- **不只"说"代码，而是直接"写"代码到文件中**（`write`、`edit`）
- **不只"推测"问题，而是直接"读"文件、"搜"代码来验证**（`read`、`grep`、`glob`）
- **不只"给出命令"，而是直接"运行"并观察输出**（`Run`）
- **处理耗时任务时进行异步管理**（`job_output`）
- **将外部资料纳入工作流**（`fetch_url`）

## 工具全景概览

当前内置工具可分为以下六大类（完整清单与 `agent_worker.json` 一一对应）：

| 分类 | 包含工具 | 典型用途 |
| :--- | :--- | :--- |
| **文件与 I/O** | `write`, `read`, `read_image`, `edit`, `glob`, `grep` | 创建、读取、修改、搜索文件与目录，读取图片/视频等媒体文件 |
| **代码执行** | `Run`, `Python`, `Bash`, `pwsh` | 执行可执行文件、bash / powershell 命令或 Python 代码 |
| **进程管理** | `job_output` | 读取、列出、导出或终止后台任务 |
| **搜索与信息** | `fetch_url`, `web_search` | 获取网页内容、执行网络搜索 |
| **状态、记忆与上下文** | `todo_write`, `todo_update`, `retrieve`, `compact` | 追踪任务进度、回溯历史、监控与压缩上下文 |
| **子代理与并行** | `subagent`, `list_agents`, `interrupt_agent`, `workflow` | 创建/列出/关闭子代理，并行分发同质任务 |

## 核心工具详解

### 一、文件与 I/O 操作

这是 coding agent 最高频使用的工具集合，直接决定了 agent 能否安全、精准地修改项目代码。

#### `write` —— 写入文件
- **功能**：将内容写入指定文件，支持 `overwrite`（覆盖，默认）和 `append`（追加）两种模式。
- **要点**：当内容超过 100 行时，规范建议拆分为多次调用，第一次用 `overwrite`，后续用 `append`。
- **示例场景**：生成全新的源码文件、配置文件或 README。

#### `read` —— 读取文件
- **功能**：按行读取文本文件，支持指定起始行（`offset`）和读取行数（`limit`），也支持从末尾倒数读取（负数 `offset`）。
- **要点**：单行长度过长时会自动截断；对于大文件，应分块读取以避免上下文爆炸。
- **示例场景**：查看现有代码结构、读取日志文件、核对配置文件内容。

#### `read_image` —— 读取媒体文件
- **功能**：读取图片、视频等媒体文件，将视觉信息转换为模型可理解的内容（支持裁剪区域与坐标说明）。
- **要点**：仅当模型具备 `image_in` / `video_in` 能力时可用，否则该工具会被自动跳过；生成或编辑图片/视频后，应立即读回结果进行验证。
- **示例场景**：查看界面截图定位问题、核对生成的图表或截图、读取设计稿。

#### `edit` —— 精准替换
- **功能**：在文本文件中进行字符串级别的批量替换，支持单行或多行内容替换，也支持替换所有匹配项（`replace_all`）。
- **要点**：这是执行**最小 diff 修改**的首选方式。相比直接覆盖整个文件，它能最大程度保留原有格式、注释和空白行，减少不必要的变更。
- **示例场景**：修改变量名、插入几行新代码、更新配置参数。

#### `glob` —— 文件模式匹配
- **功能**：基于通配符（如 `*`, `?`）查找文件，可指定是否包含目录。
- **要点**：避免使用前缀 `**` 或在过大目录中执行，以防性能问题。
- **示例场景**：快速列出所有 `.py` 文件、查找测试文件目录结构。

#### `grep` —— 内容级搜索
- **功能**：基于正则表达式在文件内容中搜索，功能相当于 `ripgrep`。
- **高级选项**：支持大小写不敏感（`-i`）、多行模式（`multiline`）、显示上下文行（`-B`/`-A`/`-C`）、文件类型过滤（`type`/`include`）等。
- **示例场景**：查找某个函数在哪些文件中被调用、定位特定错误日志模式、搜索 TODO 注释。

### 二、代码执行与进程管理

#### `Run` —— 执行程序或命令
- **功能**：直接运行指定的可执行文件（如 `git status`、`python setup.py`、`make`）。可指定工作目录（`cwd`）、环境变量（`env`）、捕获输出到文件（`output_path`），支持超时控制（`timeout`，默认 **30 秒**，范围 **1–900 秒**）。
- **Shell 模式**：默认**不经过 shell 解释器**，直接创建进程，因此不接受管道、重定向、`&&`、变量等 shell 语法；需要 shell 特性时请设置 `shell=True`（Linux/macOS 使用 bash，Windows 使用 powershell）。
- **后台运行**：显式设置 `run_in_background=True` 可将命令放入后台立即返回 `task_id`；也可用 `mode='send'` + `task_id` 向已有进程的 stdin 发送输入，并配合 `wait_for_pattern` 阻塞等待指定输出。
- **超时与保活**：等待期间按总超时 + 输出不活跃超时双条件控制；超时不会自动转后台，需要后台请显式指定 `run_in_background=True`。
- **示例场景**：编译项目（`make`, `cmake`）、运行单元测试、调用命令行工具（`git`, `npm` 等）、执行 Python 脚本。

#### `Bash` —— 执行 Bash 脚本
- **功能**：在 bash shell 中执行命令或脚本片段，支持使用 shell 特性（如管道、重定向、变量扩展等）。
- **适用平台**：主要用于 Linux / macOS 环境。
- **示例场景**：运行 shell 脚本、使用管道组合命令、执行需要 shell 解释器的复杂命令。

#### `pwsh` —— 执行 PowerShell 脚本
- **功能**：在 PowerShell 中执行命令或脚本片段，支持 Windows 特有的命令和管道。
- **适用平台**：主要用于 Windows 环境。
- **示例场景**：执行 Windows 管理命令、调用 .NET 工具、处理跨平台脚本在 Windows 上的兼容性。

#### `Python` —— 执行 Python 代码
- **功能**：在独立的子进程中执行 Python 代码，直接接收代码字符串。与 `Run` 不同，`Python` 无需通过 `python -c` 间接调用。
- **参数**：
  - `code`（必需）：内联 Python 代码，或一个以 `.py` 结尾且存在的文件路径（自动识别为文件模式）
  - `mode`：`execute`（等待完成，默认）/ `send`（后台执行，立即返回 `task_id`）/ `interactive`（启动持久 Python REPL）
  - `task_id`：已有会话 ID，传入后 `code` 会被写入该进程的 stdin 用于继续交互
  - `wait_for_pattern`：可选的输出匹配正则，阻塞等待其出现
  - `output_path`（可选）：输出文件路径，若指定则将执行输出写入该文件
  - `timeout`（可选）：超时秒数，默认 **30 秒**，范围 **1–900 秒**
  - `max_lines` / `deduplicate_output`：输出折叠与去重控制
- **执行方式**：内联代码会**始终**先写入会话目录下的临时 `.py` 文件再执行（不受长度限制），避免命令行长度问题；解析器会自动选择项目 `.venv` 解释器。
- **并发控制**：内置信号量限制，最多同时运行 8 个 Python 进程
- **后台与交互**：后台执行需显式 `mode='send'`；`mode='interactive'` 可启动持久 REPL 会话
- **示例场景**：快速验证代码逻辑、执行脚本片段、数据处理

#### `job_output` —— 获取后台任务输出
- **功能**：获取指定后台任务的累计输出，支持阻塞等待（`wait`）或定时轮询（`timeout_ms`），支持强制终止（`kill`）和导出输出（`output_path`）。
- **示例场景**：监控一个长时间运行的编译进程、查看后台测试的输出结果。

#### `Bash` / `pwsh` / `Run` 的交互式会话
这三个工具都支持以同一个工具完成“启动会话 → 继续交互”的完整流程：

1. **启动**：`Bash` / `pwsh` 使用 `interactive=True`，或 `Run` 使用 `run_in_background=True`。响应中包含 `task_id`。
2. **继续**：再次调用同一个工具，传入 `task_id=<id>`，并将 `cmd` / `command` 设为要发送的输入文本。工具会将输入写入进程 stdin，并在同一调用中返回累计输出。
3. **等待提示**：通过 `wait_for_pattern` 传入正则表达式，工具会在 `timeout` 时间内阻塞，直到匹配到对应输出。
4. **关闭**：通过 `task_id` + `cmd` / `command` 发送 shell 对应的退出命令（如 `exit`）。

`job_output` 仍可作为备用工具，用于在不发送输入的情况下读取、列出、导出或终止后台任务。

### 三、信息检索与搜索

#### `fetch_url` —— 获取网页内容
- **功能**：使用无头浏览器获取网页内容并返回 Markdown 格式。适用于抓取文档、API 说明、技术博客等。
- **示例场景**：读取某个包的官方文档页面、获取 GitHub issue 的详细内容。

#### `web_search` —— 网络搜索
- **功能**：调用网页搜索服务，返回搜索结果列表。
- **参数**：`query`（搜索词，必填）、`limit`（结果条数，建议使用精准的搜索词而非盲目调大 limit）、`include_content`（是否附带完整页面内容，开启会增加 token 消耗）。
- **示例场景**：查找第三方库的最新版本与变更、搜索报错信息的解决方案、调研竞品资料。

### 四、状态、记忆与上下文管理

#### `todo_write`
- **功能**：追踪复杂/多步骤任务的进度。支持 `pending`（待办）、`in_progress`（进行中）、`done`（完成）三种状态，每条待办还可携带 `notes`（备注）。
- **要点**：仅在复杂任务中使用，且每次更新必须传入**完整的任务列表**（也接受单个待办或别名（`todos`，兼容 `items`））；通过 `todo_push`/`todo_pop` 与 `todo_update(parent=...)` 支持嵌套子任务。对于单个条目的轻量修改，应优先使用 `todo_update`。
- **示例场景**：重构一个大型模块时，将任务拆分为"调研依赖 → 修改接口 → 更新测试 → 验证编译"并持续更新进度。

#### `todo_update`
- **功能**：通过标题定位并修改单个待办，无需重写整个列表。支持修改状态、备注和重命名。
- **要点**：优先用于轻量编辑（如标记完成、改备注、改标题）；默认启用模糊匹配以兼容标题微小差异，也支持 `force=True` 处理状态回退等边界情况。
- **示例场景**：完成某一步骤后，用 `todo_update` 将其状态改为 `done`；或在执行过程中给当前任务补充备注。

#### `retrieve`
- **功能**：仅检索历史消息（BM25 相似度 + 时间衰减，含已压缩轮次）；或按 `id`（如 `prune_0`）取回指定轮次；无持久化写入能力。
- **参数**：`query`（自然语言查询）、`id`（指定轮次引用，如 `prune_0`）、`k`（返回条数，1–10）。
- **要点**：上下文窗口是易失的；压缩/剪枝后的旧消息可通过本工具回溯，不确定历史时用它找回之前的决策、路径或结论。
- **示例场景**：压缩后回溯之前的决策、文件路径、结论；按 `prune_0` 引用取回被剪枝的完整内容。

#### `compact`
- **功能**：压缩/总结当前对话上下文以释放空间。支持 `instruction`（压缩保留指引）和 `mode`（`retentive` / `balanced` / `aggressive` / `technical` / `auto`，默认 `auto` 按当前占用自动选择）。
- **要点**：调用后存在冷却限制（默认 5 步内不可重复压缩）；压缩会损失部分细节，仅在上下文接近上限时使用。
- **示例场景**：上下文占用超过 70% 时压缩，为后续步骤腾出空间。

### 五、子代理与并行编排

#### `subagent`
- **功能**：生成一个独立的子代理来处理特定子任务。
- **示例场景**：将代码审查、文档翻译、独立模块开发等任务委派给子代理，以并行方式提升效率。

#### `list_agents`
- **功能**：列出当前所有活跃的子代理会话。
- **示例场景**：在启动多个子代理后，查看哪些子代理仍在运行或等待输入。

#### `interrupt_agent`
- **功能**：关闭指定的子代理会话，释放其资源。
- **示例场景**：子代理任务完成或异常挂起时，主动关闭会话以避免资源占用。

#### `workflow`
- **功能**：将请求**并行分发**给多个同质的子代理（swarm）。参数：`description`（任务描述）、`subagent_type`（如 `coder` / `explore` / `plan`）、`prompt_template`（含 `{{item}}` 占位符的提示词模板）、`prefix` 或 `items`（展开模板的条目列表）。
- **要点**：适合可拆分为多个独立同质子任务的场景；无法并行化的请求应说明原因而不是强行分发。
- **示例场景**：批量审查多个文件、并行调研多个主题、同时生成多个相互独立的模块。

## 如何通过提示词引导工具使用

agent 是否会调用工具、调用得是否准确，很大程度上取决于提示词的表述方式。以下是几种行之有效的引导策略。

### 1. 明确指令式（Direct Instruction）

直接在提示词中指定需要调用的工具名称和目的。

> **示例**：
> "请先用 `glob` 查找 `src/` 目录下所有的 `.cpp` 文件，然后用 `read` 逐一遍历这些文件，查找其中是否包含 `deprecated` 标记。最后将结果整理到一个新的 `report.md` 文件中，使用 `write` 写入。"

**效果**：agent 会按照你指定的工具链一步一步执行，路径清晰，可控性强。

### 2. 目标驱动式（Goal-Oriented）

不指定具体工具，而是描述期望达成的目标，让 agent 自主决策。

> **示例**：
> "我想知道这个项目的入口函数在哪里，以及它依赖了哪些第三方库。请自行搜索项目代码并给出结论。"

**效果**：agent 会自主组合 `glob` + `grep` + `read` 等工具进行调研。这种方式更适合探索性任务。

### 3. 约束条件式（Constrained Execution）

在提示词中加入显式约束，限制 agent 的行为边界。

> **示例**：
> "请修改 `config.py` 中的 `MAX_RETRIES` 值为 `5`。要求：
> 1. 必须使用 `edit` 进行最小化修改，不要覆盖整个文件；
> 2. 修改前先用 `read` 查看当前内容，确认行号；
> 3. 修改后再次用 `read` 验证结果。"

**效果**：约束条件能有效避免 agent 因"图省事"而采取不够优雅的操作（如直接覆盖文件）。

### 4. 分步工作流式（Step-by-Step Workflow）

对于复杂任务，将步骤拆解并在每一步提示中嵌入工具调用要求。

> **示例**：
> "我们需要为项目添加一个新的 CLI 命令。请按以下步骤执行：
> 1. **调研**：用 `glob` 和 `read` 查看现有 CLI 命令的实现方式；
> 2. **实现**：编写新命令的实现代码，使用 `write` 或 `edit`；
> 3. **验证**：运行 `Run` 执行相关测试，确认功能正常；
> 4. **收尾**：用 `todo_write` 更新任务进度为全部完成。"

### 5. 元提示词式（Meta-Prompting）

如果你正在设计一个系统提示词（System Prompt），可以在其中固化 agent 使用工具的通用准则。

> **示例**（可作为 system prompt 的一部分）：
> "你是一个精通工具使用的 coding agent。在执行任务时，请遵循以下原则：
> - **先观察，后动手**：修改任何文件前，优先使用 `read` 或 `grep` 确认上下文；
> - **最小化变更**：编辑文件时优先使用 `edit`，避免不必要的全文件覆盖；
> - **耗时任务异步化**：对于可能超过 10 秒的命令，使用 `Run` 并后续通过 `job_output` 监控；
> - **善用子代理**：当子任务可以独立执行且不影响主流程时，使用 `subagent` 并行处理。"

## 最佳实践与典型场景

### 场景 A：安全地重构一个函数

```text
用户：请将项目中的所有 `print_error` 调用替换为 `log_error`。

Agent 应执行：
1. grep 搜索 "print_error"，确定所有出现位置；
2. read 查看关键文件，确认是否有同名局部变量或字符串误匹配；
3. 对每个确认的文件使用 edit 进行替换；
4. 替换后 grep 再次验证是否还有残留；
5. Run 运行项目测试，确认没有破坏功能。
```

### 场景 B：处理一个交互式命令

```text
用户：请帮我运行这个交互式脚本 `setup.py` 并完成安装向导。

Agent 应执行：
1. Run 启动 `python setup.py`（若超时则转为后台任务，获取 task_id）；
2. 复用 Run 并传入 task_id + command，同时通过 wait_for_pattern 等待提示问题；
3. 在同一工具调用中发送回答并获取输出；
4. 循环步骤 2-3 直到安装完成；
5. job_output 最终确认成功信息。
```

### 场景 C：引入一个需要多文件修改的新功能

```text
用户：请为这个项目添加对 JWT 认证的支持。

Agent 应执行：
1. glob + read 调研现有认证中间件结构；
2. 撰写实现方案；
3. 按步骤修改多个文件（edit / write）；
4. todo_write 跟踪各子任务状态；
5. Run 运行测试验证。
```

### 场景 D：将外部文档纳入分析

```text
用户：请阅读附件中的设计文档，并检查代码是否实现了文档中的所有要求。

Agent 应执行：
1. 若为网页链接，使用 fetch_url 获取内容；
2. 分析内容，提取需求清单；
3. grep + read 检查代码实现；
4. 对比并输出差异报告。
```

## Plan Mode（计划模式）

Plan Mode（`/plan`）是一种**先规划、后执行**的两阶段工作流，将"方案设计"与"代码实现"解耦：

1. **生成计划** —— 由专门的规划代理（加载 `agent_planner.json`）分析需求，并将完整的执行方案写入 Markdown 文件。
2. **执行计划** —— 用户审阅计划后，再由常规的 Worker 代理负责具体实现。

#### 使用方式

```
/plan              # 默认输出到 .kimix_cache/plan_<随机>.md
/plan:roadmap.md   # 指定自定义文件路径
```

执行命令后，输入你的需求描述，以 `/end` 结束输入，或以 `/cancel` 取消。

#### 工作流程

1. **输入需求** —— 描述你要构建或重构的内容。
2. **生成计划** —— 规划代理使用 `WritePlan` / `EditPlan` 工具将计划写入文件，并自动打开文件供你审阅。
3. **确认执行** —— 输入 `y` 将计划交给 Worker 代理执行；输入 `n` 进入修订流程，可描述修改意见让 Planner 更新计划；输入 `/quit` 放弃执行。

#### 适用场景

- **复杂功能开发** —— 涉及多文件重构、架构调整或新模块开发时，预先设计能显著降低返工风险。
- **先审后做** —— 在执行任何代码修改前审阅计划，便于调整范围或拆分任务。
- **职责分离** —— 规划代理专注架构设计，Worker 代理专注代码实现，提升整体质量。

## 总结

内置工具是 coding agent 从"语言模型"进化为"可执行代理"的桥梁。掌握这些工具的特性与适用场景，并在提示词中清晰、合理地引导其使用，是发挥 agent 最大效能的关键。

**核心原则回顾**：

1. **观察先于行动**：`read` / `grep` / `glob` 永远是修改前的第一步。
2. **最小化改动**：`edit` 是编辑文件的首选，`write` 仅用于创建新文件或明确需要整体重写的情况。
3. **耗时任务异步化**：善用 `Run` 的超时自动转后台机制，结合 `job_output` 管理交互与长时任务。
4. **外部信息无缝整合**：通过 `fetch_url` 将外部信息纳入分析。
5. **先规划后构建**：对于复杂任务，使用 `/plan` 将设计与实现分离。

通过刻意地在提示词中植入这些原则，你将能够让 agent 更加可靠、高效、可控地完成各类软件开发任务。
